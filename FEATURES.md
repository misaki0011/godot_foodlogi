# Fresh Routes — Features

Extracted from `SPEC.md`. Status reflects actual implementation state, not spec intent — update both files together when scope changes.

Status legend: **Done** (built and verified) · **In Progress** · **Planned** (MVP scope, not started) · **Backlog** (explicitly post-MVP per §13/§14) · **Retired** (built once, since removed from the game).

The Godot build is a 3D-isometric port of `fresh-routes-mvp.html`, the reference prototype. Where the HTML differs from SPEC.md's exact wording, the port follows the HTML (see the note after the table).

| ROUTE-05 | Route upgrade/bulldoze | Done | P1 | ROUTE-01, ROUTE-04 | A route tile can be upgraded Dirt→Paved→Main for a flat cost; bulldozing any built tile removes it with **no refund**, matching the HTML (this is a deviation from the old 50%-refund behavior). A **hub, a storage building and a bridge are all structures built on top of a route tile**, so bulldozing one takes only the structure and hands the road back **at the level it already was** (Dirt/Paved/Main), connections intact — the player paid for that paving separately and never asked to lose it. A bridge tile keeps its own `level` throughout; hub and storage cells replace the route cell outright, so `Main._do_build_hub`/`_do_build_storage` record the covered level on the cell for `_clear_cell` to restore — clearing the road too would swallow infrastructure the player never asked to lose and split the network in half. A cleared bridge additionally drops its deck connections while keeping the road beneath (`Main._clear_cell`): the deck is the road that ceases to exist, and without that the two roads the crossing kept apart would silently merge. Only a **bare route tile** is removed outright, so clearing a built-up tile takes two bulldozes — one for the building, one for the road; taking a building down is deliberately a different act from taking the road away. Either action can also be swept across many tiles in one drag (see ROUTE-15), under the same rule. | §2.1, §3.4 |

| ROUTE-17 | Bridge: cross a route without joining it | Done | P2 | ROUTE-12, HUB-05 | A **placed structure**, not a drag-time effect: the Bridge tool (§60) converts one existing route tile carrying a straight through-run of road into a road-over-road crossing, the single paid exception to ROUTE-12's interior-must-be-empty-ground rule. The road already there keeps running underneath; a raised deck spans it at right angles, and a later drag may run **straight over the deck** -- entered and left in the same direction -- without the two routes ever becoming one network. Connectivity becomes a property of a `(tile, lane)` graph vertex rather than a tile (`SimulationEngine.LANE_GROUND`/`LANE_DECK`): the lane you land on is decided by the step's direction, and from either you may only leave the way you came in, so `find_path`, `road_components` and `established_route_cells` all keep the two roads separate with no second grid layer and no change to `GameState.connections`. Costed to lose to a detour: §6/day extra upkeep (added after any hub discount, since the deck is a structure not road surface), 2x freshness decay to cross the deck (weighted into Dijkstra so it prefers going around), shared tile capacity, and a cap of **2 bridges per connected road network** -- an existing bridge counting against both networks it serves. ## Known deviation from SPEC.md v0.3 text

SPEC.md v0.3 §0/§4.1/§4.4 describes **atomic** hub-forming route placement: if a new route tile would require a Small Hub the player can't afford, or the network is already at its hub cap, the whole placement (route + hub) should be rejected with no map change and no charge. `fresh-routes-mvp.html` — the reference this port originally followed — instead implemented the earlier v0.2 behavior: the route tile is placed and charged immediately, and a separate `checkAutoHubs` pass afterward either auto-builds the hub, marks the tile `needsHub` (funds too low), or marks it `hub_capped` (network at cap). This port has moved past both of those: hub construction is a separate, manual, player-paid action via the Build Hub tool, buildable on any existing route tile subject only to the per-network cap (HUB-01, HUB-06; v0.5 item 17) — see SPEC.md §0 changelog and "Manual hub construction on any route tile" under §4.4. Neither the HTML's auto-build nor SPEC.md's atomic-rejection describes current behavior; both are kept in their respective docs as historical/aspirational context only.

## Known deviation from fresh-routes-mvp.html's node positions

The HTML places Farm at (3,4) and Bakery at (3,9), only 2-3 tiles (Chebyshev distance) from Garden at (2,6), and both sit close enough to the grid edge that a wide supply bubble could run off-map. With TERR-03's always-on supply speech bubbles, sources that close together (or that close to the edge) crowded or clipped their bubbles. This port moves Farm to (3,2) and Bakery to (3,11) so every source is at least 4 tiles from every other source and at least 2 tiles from the grid's outer edge (valid range x:[2,18], y:[2,11] on the 21x14 grid). Harbor also moved one tile, from (17,9) to (18,9): once bubbles doubled in size, Harbor's supply bubble started overlapping City E's demand bubbles on screen (only 2 tiles apart) even though no source-spacing rule was violated -- source-to-settlement distance was never constrained before. Garden and Dairy keep their original HTML coordinates. Supply amounts, food mappings, and all other node positions are unchanged.
